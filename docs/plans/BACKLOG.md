# Backlog

Plans and ideas not yet committed to a milestone. When an item moves into active build, it gets its own ephemeral working doc at `docs/plans/<TOOL_NAME>.md` (see [../ADDING_A_TOOL.md](../ADDING_A_TOOL.md)) and is removed from this list.

## UX

- **Drag-and-drop input on dashboard/tools.** Drop one or more files anywhere on the dashboard or a tool screen to start a flow. Was a stretch goal for 0.2.0; still unshipped.
- **Paste-from-clipboard for image inputs.** Any tool that accepts images should allow pasting (Ctrl/Cmd+V) directly — screenshots in particular. Likely a shared input affordance rather than per-tool.
- **Video thumbnails in the staging area.** Show a first-frame thumbnail next to each picked video so the user can confirm the file before converting. Two viable paths: (a) `<video src={convertFileSrc(path)}>` with asset-protocol scope extended for picked video paths — fast to build but only renders codecs the WebView decodes natively (mp4/webm yes, mkv/avi no — would need a placeholder); (b) a new `extract_thumbnail` Tauri command that runs ffmpeg to grab a JPEG of the first frame and returns bytes via IPC — works for every codec ffmpeg can read, more plumbing. Deferred from the Video Format Converter v1 build.

## Future tools

### Image

- **HEIC support for the Image Format Converter.** Researched 2026-05-25; deferred. The `image` crate has no HEIC support. Standard Rust path is [`libheif-rs`](https://crates.io/crates/libheif-rs) / [`libheif-sys`](https://github.com/Cykooz/libheif-sys), which wrap [libheif](https://github.com/strukturag/libheif) (C). The pdfium "download a prebuilt tarball in build.rs" pattern doesn't transfer: libheif itself is just a container parser — HEIC decoding needs an HEVC backend ([libde265](https://github.com/strukturag/libde265)), and there's no canonical all-in-one prebuilt distribution. `libheif-sys`'s `embedded-libheif` feature vendors libheif's source and builds it via CMake, but does NOT bundle codec deps; libde265 must still be installed at build time. The closest precedent for a single-blob libheif is [pphh77/libheif-Windowsbinary](https://github.com/pphh77/libheif-Windowsbinary/releases) — Windows-only, single maintainer. Realistic options when picking this back up:
  - Use `libheif-sys` with `embedded-libheif`; require `libheif`/`libde265` system installs on dev + CI (apt / brew / `cargo vcpkg build`); later stage the per-OS shared libs as Tauri resources for end-user bundles.
  - Build libheif + libde265 from source in `build.rs` end-to-end (heavy: minutes-long first build, cmake + C++ compiler required on every builder).
  - Wait for the ecosystem (pure-Rust HEVC decoder, or an "all-in-one" prebuilt libheif). HEVC patents make a pure-Rust decoder unlikely soon.
  HEIC **encode** is doubly out of scope: needs x265 (GPL + patent-encumbered).
- **Image Compress: preserve PNG output via palette quantization.** v1 redirects PNG inputs to lossy WebP because PNG itself has no quality knob and a lossless re-encode wouldn't move the slider. A format-preserving path would use [`imagequant`](https://crates.io/crates/imagequant) 4 (pure Rust, GPL — fine, the ffmpeg bundle already pulls us under GPL) for the lossy palette quantization plus [`oxipng`](https://crates.io/crates/oxipng) 10 (MIT, pure Rust with `freestanding`) for a lossless post-pass. Slider would map to palette quality (0–100) instead of JPEG/WebP quality 1–100; emitting palette PNGs goes through the lower-level `png` crate (already transitive via `image`) since `image` 0.25's PNG encoder doesn't expose palette output cleanly. Cost: ~2–3 hrs + new encoder lane + DECISIONS entry. Picked the WebP redirect in v1 (2026-05-31 with [@alex-yokisama-drewl]) on the "one encoder lane, one slider semantics" axis; revisit if smoke shows users wanting their PNGs back as PNGs.
- **Image Compress: preserve TIFF output via in-format compression.** v1 redirects TIFF inputs to WebP because `image` 0.25's TIFF encoder doesn't expose LZW / Deflate / PackBits cleanly and TIFF's lossy options (TIFF-JPEG) are weird and poorly supported. A format-preserving path means either picking the lossless TIFF compression that ships with `image` (slider becomes a no-op for TIFF inputs — meaning splits per format) or pulling in a richer TIFF encoder (`tiff` crate direct). Same call as the PNG entry: revisit if users want their TIFFs to stay TIFFs.
- **B&W text color normalizer.** A tool that makes roughly-black-and-white images of text more readable to the human eye — photographed or scanned pages where the "white" is a grey-beige gradient and the "black" is a washed-out dark grey. Scope, algorithm (global threshold vs. adaptive/local, e.g. Sauvola; whether to keep anti-aliased edges or go hard-binary), and whether it ships as its own tool or a mode of an existing one are all **still open — to be designed with @alex-yokisama-drewl before any build starts.** Raised 2026-11-27.

- **Image Compress: animated PNG / WebP inputs.** v1's picker doesn't filter them out (they share extensions with static variants); `decode_oriented` returns the first frame so they re-encode as a static lossy WebP. Acceptable v1 behaviour; backlog the "preserve animation" follow-up — needs animated-WebP encode support (`webp::AnimEncoder` exists) and a per-tool "animation detected, first frame only" warning shape.

### Video

- **Compress: scale audio bitrate with the quality slider.** v1 of Compress stream-copies audio (`-c:a copy`) so the slider only affects video bitrate. For sources that are mostly audio (podcast clips, music videos at low video bitrate) the slider has little effect on overall file size. Add a checkbox (default off) that switches the audio path from `-c:a copy` to a re-encode whose bitrate scales with the slider — e.g. AAC 64k at `slider=0` → 192k at `slider=1`, with parallel ranges for Opus / MP3 (`-q:a 7` → `-q:a 2`) / Vorbis. Backlog because v1's stream-copy gives bit-perfect audio for free; this is purely additive once smoke confirms the v1 shape.
- **Trim: HDR color metadata pass-through.** The frame-accurate re-encode landed at `b3c6442…` mirrors codec + pixfmt + audio codec but doesn't read or pass through the `color_primaries` / `color_trc` / `colorspace` triplet (bt2020 / smpte2084 / bt2020nc on real HDR sources). Result: an HDR input round-trips as SDR-tagged after re-encode — a visible regression on HDR displays. Fix: extend [`ffmpeg::probe_video_stream_params`](../../src-tauri/multitool-core/src/ffmpeg.rs) to parse the `(tv, bt2020nc/bt2020/smpte2084)` annotation that already lives in the pixfmt-paren slot, then thread `-color_primaries` / `-color_trc` / `-colorspace` through [`build_reencode_args`](../../src-tauri/multitool-core/src/tools/video_trimmer/convert.rs). Defer until a real HDR clip is in the smoke-test rotation (none today). Decision context in [DECISIONS.md → "Video Trimmer"](../DECISIONS.md).
